# 模型假設與警示規則草稿

> 狀態：供成員 A、B 與指導教授確認的 MVP 草稿。本文中的門檻與機率不是經企業歷史資料估計的結論；確認前不可描述成已驗證的預測能力。

## 1. 分析範圍與資料假設

- 一列 CSV 是一個部門、費用類別、月份的預算與實際支出；金額為同一幣別，`budget` 是月預算。
- 每次分析以資料中最新年度作為目標年度。月度部門預算與實際支出先加總，再計算使用率與差異。
- 年預算基準目前以平均月預算乘 12 推算；What-If 可用 `annual_budget` 覆寫。若年度預算有季節性或逐月分配差異，這個簡化推估可能不準確。
- 完整 YTD 指資料從 1 月連續涵蓋到最新月份。缺月資料無法代表完整的已過時間；不得把「有幾筆觀測月份」直接視為「已過幾個日曆月」來發出執行進度警示。
- 當前 API 的 CSV 年度彙總、run-rate 預測與示範貝氏網路均是 MVP 分析，不包含未入帳承諾支出、預算調整歷史或部門人力等外部變數。

## 2. 貝氏網路結構與參數

圖模型為 `歷史速率 → 超支風險`、`當前進度 → 超支風險`、`季節因素 → 超支風險`。給定證據後，以 Variable Elimination 計算：

`P(超支 | 已觀測證據)`

### 暫定根節點先驗

| 節點 | 狀態 | 先驗 | 假設來源／意義 |
|---|---|---:|---|
| 歷史速率 | 快／持平／慢 | 0.25／0.50／0.25 | 暫假設去年超支、接近預算、低於預算的機會；不是樣本估計。 |
| 當前進度 | 提前／落後 | 0.50／0.50 | 暫假設兩種進度各半；目前二元分類把「按計畫」也放在落後一側，見下方限制。 |
| 季節因素 | 旺季／淡季 | 0.30／0.70 | 暫假設旺季約占三成；未使用企業或產業月度資料校準。 |

### 條件機率表（CPT）公式

程式目前使用可加分數：

`P(超支 | h, p, s) = clip((5 + 歷史分數 + 進度分數 + 季節分數) / 100, 0, 1)`

| 證據狀態 | 對超支分數的加值 |
|---|---:|
| 歷史速率＝快／持平／慢 | +30／+12／+0 |
| 當前進度＝提前／落後 | +45／+0 |
| 季節因素＝旺季／淡季 | +15／+0 |
| 所有證據組合的基礎分 | +5 |

例如「歷史快、進度提前、旺季」的條件超支機率為 `(5+30+45+15)/100 = 95%`。分數表是專家規則式 CPT，並非從資料學得；加分獨立相加亦隱含了簡化假設。教授若認為條件機率表缺乏統計依據，應優先改用有標籤的歷史年度資料估計或校準 CPT，並做時間外驗證。

### 連續資料轉離散狀態

- 歷史速率：前一年度實際/預算 `>1.05` 為「快」，`<0.95` 為「慢」，其餘為「持平」。沒有上一年度或上一年度預算為零時，不提供該節點證據。
- 當前進度：目前程式以 YTD 實際/年度預算與已過月份占比比較；高於占比為「提前」，否則為「落後」。這是二元簡化分類，並不等於「超支／不超支」。若資料月份不完整，必須修正 elapsed-month 計算或不提供此證據。
- 季節因素：目前以最新月實際支出除以觀測月平均作自身倍率，產業倍率固定 1.0，再按 0.4/0.6 加權、門檻 1.5 分旺淡季。樣本少時代表性弱；固定產業倍率不是真正的產業季節資料。
- 未觀測節點由網路依先驗邊際化。先驗會直接影響後驗結果，應在 UI/報告說明資料來源與校準狀態。

## 3. 年底預測與區間假設

- 1 月至最新月完整連續：點估計為 YTD 實際支出加上剩餘月份乘以觀測平均月支出。
- 月份不完整：點估計為觀測月平均實際支出乘以 12；回傳 `forecast.method = annualized_observed_months`。
- 至少兩個觀測月份時，使用樣本標準差與 Student-t 臨界值估計區間及超過年度預算的尾端機率；少於兩個月則區間和 run-rate 機率為 `null`。
- `ci95` 在目前實作中是依簡化月度支出變異推得的模型區間。由於資料量小、月份可能相關、趨勢/季節性未建模，對外可稱「模型估計的 95% 區間」，不可暗示為已回測保證覆蓋率的正式信賴區間。
- `forecast.overrun_probability` 是 run-rate 分布超過年度預算的機率；`forecast.bayesian_overrun_probability` 是離散貝氏網路後驗機率。兩者依據不同，UI 和簡報必須標明，不可混成一種機率。

## 4. 警示規則（暫定，待 A/B/教授確認）

### A. 預算可能不足

使用 run-rate 模型，不直接拿當月使用率當作年底超支結論：

1. `forecast.overrun_probability >= 0.67`：高風險／紅色，提示「依目前支出速度，年底超過年度預算的模型機率偏高」。
2. `0.33 <= forecast.overrun_probability < 0.67`：注意／黃色，提示「預測區間存在超支風險，建議檢視未來承諾支出」。
3. `< 0.33`：目前未達預警門檻／綠色，不代表保證不超支。
4. 機率為 `null`：標示「資料不足，暫無法估算」，不得假裝是低風險；目前 API 的燈號 fallback 到貝氏機率僅為暫定 UI 行為，應另保留資料不足註記。

建議警示附上 `year_end_amount / annual_budget` 預測比率與區間是否跨越預算線。點估計超預算但區間很寬時，文案應表達不確定性；若區間下限已高於年度預算，才可描述成「目前模型區間整段高於預算」，仍不得稱為確定超支。

### B. 執行進度落後

這是「實際支出進度慢於時間／計畫進度」的執行狀態，不等於預算不足或節省成功。先限於**完整 YTD** 且有效年度預算大於零的資料：

`progress_gap = YTD 實際支出 / 年度預算 - 已過月份 / 12`

| 條件 | 警示 |
|---|---|
| `progress_gap <= -0.10` | 執行落後（黃色）：支出進度至少落後時間進度 10 個百分點。 |
| `progress_gap <= -0.20` | 嚴重落後（橘色或紅色，由 A/B 統一視覺定義）：至少落後 20 個百分點。 |
| `-0.10 < progress_gap < 0.10` | 大致符合進度；不發落後警示。 |
| `progress_gap >= 0.10` | 支出進度提前；可提示檢查未來承諾支出，但不能僅據此判定年底超支。 |

如果月份缺漏、資料尚未涵蓋 1 月至最新月份，回傳「月份不完整，無法判斷執行進度」，而不是發出落後警示。未來若 CSV 能提供每月計畫預算，可改為比較「累計實際支出／累計計畫預算」，更適合預算不均勻的部門。

### C. 警示優先順序與文字

- 預算不足與執行落後可同時成立，應作為兩個獨立 alert 回傳；不能因一項綠燈蓋掉另一項警示。
- 每項警示至少包含 `code`、`severity`、`title`、`message`、`evidence`、`recommendation`。證據應帶實際值與門檻，讓使用者能追溯原因。
- 建議初版採規則模板產生中文診斷，輸入只取模型輸出與資料欄位；不需要依賴語言模型。若之後採用 LLM，必須限制其只摘要已計算證據，不得自行產生數字或因果結論。
- 「主因」須避免因果措辭。可說「模型中對風險提升最大的觀測因素」，不可宣稱已證明某支出項目造成超支。

## 5. 尚待確認與驗證工作

1. A/B 與教授確認先驗、CPT 加分表及 33%/67%、10/20 個百分點門檻是否只作展示規則。
2. 決定 `當前進度` 是否由二元改為「提前／符合進度／落後」，或保留貝氏節點二元、另用三段式進度警示。
3. API 已調整為只有 CSV 從 1 月連續涵蓋至最新月時，才將「當前進度」送入貝氏網路；缺月資料不再以觀測筆數代替日曆月份。後續仍須實作明確的資料完整性／執行進度警示。
4. 準備未參與規則設計的測試 CSV 情境，記錄每個警示是否符合預期；資料不足情境也要有明確結果。
5. 將確認後的規則映射到 API JSON 與前端文案，再進行效能及整合測試。
